## Session 2 — The lightbox, and a full-screen overlay that ignored every click

### The find worth keeping

**Nothing in the card lightbox responded to a tap** — not the close button, not the
backdrop, not the card. Only `Escape` worked, and only because that listens on `window`.

The cause was never in the lightbox. `lead-detail-sheet.tsx` renders it *outside*
`</SheetContent>`, and a modal Radix sheet uses `react-remove-scroll`, which injects:

```
.block-interactivity-<id> { pointer-events: none; }   ->  <body>
.allow-interactivity-<id> { pointer-events: all; }    ->  the sheet content only
```

Everything under `<body>` inherits `none`; only the sheet's own subtree gets it back. A
`fixed inset-0 z-[60]` overlay sitting outside is therefore completely inert, and its
z-index is irrelevant. Fix: `pointer-events-auto` on the overlay root — a declared value
beats an inherited one whatever the specificity. Recorded in `01-architecture.md`.

**This was not new.** The previous lightbox rendered in the same place, so the original
report that "the card enlarge is not working properly" was most likely always this.

**And the part to sit with:** typecheck, lint and 170 tests passed for the entire time
the component was dead. Nothing automated in this project can see a click that never
lands. Anything interactive needs a human to touch it.

## Session 1 — The admin table can see past today

### What was done

`/admin` showed only leads created today, so when the date rolled over, a whole day's
work read as lost. Fixed by giving it the date pills `/leads` already had.

- **`src/lib/lead-range.ts` (new)** — `RANGES` (**Today / 7 days / All**) and `startOf()`,
  lifted out of `leads-list.tsx` so both screens share one definition. Twelve tests in
  `lead-range.test.ts` pin the day boundaries, which is the part that goes wrong quietly.
- **`src/lib/mongo.ts`** — `listTodaysLeadsFromAtlas` -> `listRecentLeadsFromAtlas`, date
  filter gone, limit 200 -> 500.
- **`src/lib/salesforce/lead.ts`** — `CreatedDate = TODAY` -> `LAST_N_DAYS:30`,
  `ADMIN_LIMIT` 200 -> 500, renamed to `listRecentEventLeads`.
- **`admin-leads.tsx`** — a range pill row above the status pills, chaining
  `leads -> inRange -> stats -> shown -> CSV`, with the CSV filename naming the range.
- **`leads-list.tsx`** — imports the shared module; loses its "30 days" pill.

Commit `1e4979d`. typecheck, lint, **165 tests** all pass.

### The bug underneath the bug

The admin cutoff was computed **on the server**:

```js
const since = new Date();
since.setHours(0, 0, 0, 0);   // Hostinger's midnight, probably UTC
```

For an IST admin that starts the day at 05:30 local, so the early morning's leads fell
off a day early. `/leads` never had this because its `startOf()` runs in the browser.
Moving the filter client-side fixed the timezone as a side effect — no offset passed to
the server, no URL params, no round trip per pill. That is the whole reason this approach
was chosen over plumbing a timezone through.

### Verified against real data

```
listRecentLeadsFromAtlas -> 8 leads
  today -> 0     (everything is 11-12 Sep; today is the 13th)
  7     -> 8
  all   -> 8
```

Exactly the reported bug, now filtered rather than hidden.

**A scare worth recording:** three consecutive queries returned 9, then 8, then 7 leads.
Not a bug — the user was deleting test leads through the app while the queries ran. A
single script running `countDocuments()` and `listRecentLeadsFromAtlas()` together
returned 7 and 7. Check atomically before believing a count has drifted.
